\begin{abstractpage}
Sinhala is a low-resource language with limited digital resources for formal written communication. Although modern Large Language Models can generate Sinhala text, they often struggle with formal letter writing because of limited exposure to Sinhala administrative writing, strict structural conventions, honorific usage, and the distinction between spoken and written Sinhala. This research presents SinhalaLipi, a Retrieval-Augmented Generation based system for generating formal Sinhala letters from informal user prompts.

The proposed system combines structured information extraction, missing-information collection, semantic retrieval, prompt augmentation, and LLM-based generation. A curated Sinhala formal letter corpus is embedded using LaBSE and indexed with FAISS so that relevant letter structures and examples can be retrieved for each user request. The implementation includes a React-based user interface, a FastAPI backend, a modular RAG pipeline, a plug-and-play LLM factory, and feedback mechanisms for collecting user ratings and improving the knowledge base.

The system was evaluated using 30 formal letter prompts across multiple categories and five expert evaluators. The expert evaluation compared SinhalaLipi outputs against direct LLM baseline outputs using grammar, structure, contextual relevance, formality, fluency, and overall usability criteria. Results show that the RAG-based approach outperformed the direct LLM baseline across all evaluation dimensions, with experts preferring SinhalaLipi outputs in 82.7 percent of pairwise comparisons. These findings indicate that retrieval augmentation can improve the quality, structure, and practical usability of formal Sinhala letter generation in a low-resource language setting.
\end{abstractpage}

\chapter{Introduction}

\section{Problem Statement}
This research addresses a critical gap in Sinhala language processing, specifically in the domain of formal letter writing. Formal Sinhala letters are essential to official communication across government, educational, and corporate settings in Sri Lanka, yet current Large Language Models (LLMs) are ill-equipped to generate them accurately. This deficiency stems from the scarcity of Sinhala-specific training data, the morphological complexity of the language, and the strict structural conventions governing formal correspondence. This research proposes and evaluates a Retrieval-Augmented Generation (RAG) based pipeline that generates high-quality formal Sinhala letters from informal user prompts. The system extracts structured intent from the prompt, retrieves relevant example letters from a curated knowledge base, and guides a multilingual LLM to produce contextually appropriate, grammatically correct, and properly structured formal letters. This work contributes to the broader goal of improving LLM support for Sinhala as a low-resource language, offering a practical framework that can serve as a foundation for future research in formal Sinhala text generation.


\section{Research Questions}
\subsection{Main Research Question}
How can a Retrieval-Augmented Generation approach be used to generate high-quality formal Sinhala letters from informal user prompts using Large Language Models?

\subsection{Sub Research Questions}
\begin{enumerate}
    \item What are the limitations in current Large language Models in generating formal Sinhala text?
    \item Can Dense Vector Indexes such as FAISS Index incorporated with LaBSE effectively retrieve the relevant Sinhala Texts to generate the expected text?
    \item How does the RAG-based letter generation system compare with a standard LLM baseline in producing formal Sinhala letters, as measured through human expert evaluation of grammatical correctness, structural adherence, contextual relevance, and formality appropriateness?
    \item What evaluation criteria and rubrics are most effective for assessing the quality of generated formal Sinhala letters, given the absence of established automated metrics for low-resource Sinhala?
    \item What are the limitations when applying a RAG approach to low-resource languages like Sinhala?
\end{enumerate}

\section{Research Objectives}

The primary objective of this research is to generate high-quality formal Sinhala letters from informal user prompts through a Retrieval-Augmented Generation approach that combines semantic search with multilingual language models. The specific objectives are:

\begin{itemize}
    \item \textbf{Develop a two-stage retrieval architecture} combining FAISS-based dense vector search with cross-encoder reranking to improve precision in retrieving relevant Sinhala letter examples, addressing the limitations of single-stage embedding similarity approaches.
    
    \item \textbf{Implement automated information extraction} using fine-tuned XLM-RoBERTa transformers to parse informal Sinhala user prompts into structured fields (letter type, recipient, subject, purpose), enabling template-based letter generation with minimal user burden.
    
    \item \textbf{Establish a curated Sinhala letter corpus} with structured metadata (category, formality level, document type) and privacy-preserving anonymization to serve as a reusable knowledge base for formal writing tasks across diverse contexts.
    
    \item \textbf{Evaluate the RAG approach against baseline LLM generation} through comparative analysis measuring grammatical correctness, structural adherence, contextual relevance, and formality appropriateness using human expert assessment.
    
    \item \textbf{Design a continuous improvement mechanism} where highly-rated user-generated letters are incorporated back into the knowledge base, creating a self-improving feedback loop that expands coverage and quality over time.
    
    \item \textbf{Employ and assess multilingual models} (LaBSE for embedding, XLM-RoBERTa for information extraction, and provider-agnostic generation models, with Google Gemini 2.5 Flash used in evaluation and Aya 8B supported for local deployment) on low-resource Sinhala tasks, contributing empirical evidence on cross-lingual transfer capabilities for under-resourced languages in specialized domains.
    
    \item \textbf{Provide a reproducible open-source framework} deployable on modest hardware using local inference (Ollama), eliminating dependency on commercial APIs and ensuring research accessibility for low-resource language communities.
\end{itemize}

\section{Hypothesis}

This research aims to test the following hypotheses regarding the effectiveness of Retrieval-Augmented Generation for formal Sinhala letter generation:

\subsection{Null Hypothesis (H0)}
There is no significant difference in grammatical errors, correctness, fluency and contextual relevance of formal letters written in the Sinhala Language generated by a standard Large Language Model compared to those generated using a Retrieval-Augmented Generation approach.

\subsection{Alternative Hypothesis (H1)}
The use of a Retrieval-Augmented Generation (RAG) approach significantly improves the fluency, grammatical correctness, and contextual relevance of Sinhala formal letters compared to generation by a standard language model alone.

\section{Significance of the Study}

This study contributes to Sinhala natural language processing by addressing a practical writing task that is important in Sri Lankan educational, administrative, and professional contexts. Formal Sinhala letter writing requires correct structure, written register, honorific usage, and contextual appropriateness, all of which remain difficult for general-purpose LLMs in a low-resource language setting. By combining a curated Sinhala letter corpus with retrieval-augmented generation, this research demonstrates a practical method for improving domain-specific Sinhala text generation without requiring large-scale model training.

\section{Scope}
This research targets a RAG based approach to generate formal Sinhala texts for relevant user prompts. Suitable models for transforming user texts, embedding the user prompts and generating text have been used. The following describes what falls within and out of the scope of this research.

\subsection{In Scope}

\begin{itemize}
    \item The research focuses mainly on formal letters which are used in formal requests, invitations, and official communications.
    \item Information extraction from user prompts using a transformer model and interacting with the user to obtain missing information if there are any to generate the letters. 
    \item Developing a RAG based approach for formal letter generation in Sinhala Language.
    \item Using LaBSE for creating text embeddings.
    \item Using FAISS to store the example data in Sinhala and for semantic retrieval of similar examples for user prompts.
    \item Qualitative evaluation of the generated outputs for the user prompts using human assessment. 
    \item Data from three sources have been combined and preprocessed to form the retrieval knowledge base: (1) formal letter questions and model answers derived from GCE Ordinary Level Sinhala examination and model papers, capturing the structure, conventions, and templates of formal Sinhala letters across letter types; (2) letters written by students who passed the GCE O/L Sinhala examination for these prompts; and (3) a collection of high-quality real-world formal Sinhala letters obtained from institutions and personal contacts.
\end{itemize}

\section{Out of Scope}

\begin{itemize}
    \item Formal Sinhala texts other than formal letters, such as notices, newspaper articles, essays, meeting minutes, and posters, are not covered in this research.
    \item Generation of informal or spoken Sinhala text is outside the scope of this research.
    \item Building a comprehensive Sinhala NLP pipeline, including tokenizers and morphological analysers, is not considered.
    \item Post-generation error correction and grammar checking in the generated text are not addressed.
    \item Extension of the approach to other low-resource languages is left for future work.
\end{itemize}

\section{Contribution}
This research makes the following contributions towards improving Large Language Model support for Sinhala, a low-resource language:

\begin{itemize}
    \item \textbf{A retrieval-augmented generation pipeline for formal Sinhala letter writing} that combines structured information extraction, missing-information collection, semantic retrieval, cross-encoder reranking, and prompt augmentation to generate formal letters from informal user prompts.
    \item \textbf{A curated Sinhala formal-letter corpus} with structured metadata and privacy-preserving anonymization, assembled from examination papers, student-written letters, and real institutional correspondence, which can be reused as a knowledge base for future Sinhala formal-writing research.
    \item \textbf{An evaluation framework and rubric} for assessing formal Sinhala letter quality through human expert judgement, addressing the absence of established automated metrics for low-resource Sinhala generation.
    \item \textbf{Empirical evidence} that retrieval augmentation significantly improves the grammar, structure, formality, fluency, and overall usability of generated formal Sinhala letters compared with a direct LLM baseline.
    \item \textbf{A reproducible, provider-agnostic, open-source system} (SinhalaLipi) that decouples the retrieval pipeline from the underlying LLM, enabling the same approach to be deployed across cloud and local inference environments.
\end{itemize}

These contributions can serve as a foundation for extending similar retrieval-augmented methods to other formal Sinhala text types and to other South Asian low-resource languages.

\chapter{Literature review}

Large Language Models (LLMs) are deep neural network architectures trained on vast amounts of text data to understand and generate human language \cite{33}. The evolution of LLMs traces back to early neural language models, but the field witnessed a paradigm shift with the introduction of the Transformer architecture in 2017, which enabled efficient parallel processing of sequential data through self-attention mechanisms. This breakthrough led to the development of influential models such as BERT (Bidirectional Encoder Representations from Transformers) and GPT (Generative Pre-trained Transformer), which demonstrated unprecedented capabilities in natural language understanding and generation tasks \cite{33}. Over the years, LLMs have grown dramatically in scale and sophistication, with models like GPT-3, GPT-4, LLaMA, and BLOOM \cite{30} \cite{32} containing billions of parameters and exhibiting emergent abilities such as few-shot learning, reasoning, and multilingual understanding. These advances have revolutionized numerous applications including machine translation, question answering, text summarization, and code generation. However, despite their remarkable performance on high-resource languages like English, LLMs continue to face significant challenges with low-resource languages, where training data scarcity limits their effectiveness \cite{33}.

\section{Sinhala NLP Resources}
Sinhala is an Indo-Aryan language spoken by over 16 million people \cite{2}. However, it still remains under-resourced as a language in the NLP domain. Even though there is high resource availability for languages like English, when it comes to Sinhala, the resource availability, more importantly, the quality of resources, remains low. According to the widely-cited language resource classification by Joshi et al. (2020), Sinhala is a Class 1 “extremely low-resource” language, reflecting the paucity of corpora and NLP infrastructure \cite{joshi2020}. To understand this properly, we need to take a look back at the evolution of Sinhala as a language in the NLP domain. Fundamental resources such as part-of-speech taggers and morphological analysers exist, but only for limited domains. As noted by Nisansa et al., most of the morphological analysers developed are rule-based \cite{1}, and even those that incorporated machine learning, such as the morphological analyser by Welgama et al. \cite{3}, have not made their results or resources publicly available. The one that stands out, with a comprehensive vocabulary, is `sinMorphy', which is also rule-based and achieved an accuracy of 85.2\%.

Two specific areas highlighting these gaps are grammatical error correction and text summarization in Sinhala. In English and other high-resource languages, grammatical error detection and correction (GEC) has seen large benchmarks and neural models, but Sinhala has no comparable dataset or widely-used system. The few studies on Sinhala grammar have been largely rule-based or limited in scope. For instance, Sewwandi et al. (2021) developed a rule-based grammar checker to help primary school students identify errors in Sinhala sentences \cite{5}. Their system applied handcrafted grammatical rules (focused on basic active-voice sentence structure) and offered corrections, but such an approach cannot scale to the complexity of open-domain Sinhala text. More recently, Jayasuriya et al. (2023) presented a study on Sinhala grammatical error correction (GEC) as a “case study” of low-resource GEC \cite{6}. They emphasize that GEC is crucial for improving Sinhala writing quality and attempt to build a model despite the lack of data. Their rule-based approach has shown over 90\% accuracy for gender-based noun detection in complex Sinhala sentences, which is also limited in scope when considering the Sinhala language as a whole. Unlike English, which has large GEC corpora (e.g., CoNLL-2014 \cite{7}, BEA-2019 \cite{8}), Sinhala lacks a robust error-annotated corpus, and only scoped or prototype grammar correction tools have been reported \cite{1}. This represents a clear gap in resources and a challenge to developing high-accuracy grammar correction for Sinhala text.

Similar observations apply to text summarization in Sinhala. Early research in Sinhala summarization was limited to extractive or heuristic methods on small datasets. For example, Welgama (2012) proposed a deterministic algorithm for Sinhala text summarizing, and Wimalasuriya (2019) explored summarization in a doctoral study, likely using manually crafted methods. These early works, while pioneering, did not have the benefit of large-scale training data. In recent years, there have been a few attempts to apply modern summarization techniques. Jayawardane (2022) investigated abstractive and extractive summarization specifically for government gazette documents in Sinhala, and Rathnayake et al. (2023) experimented with summarizing Sinhala textbooks \cite{9}, comparing extractive vs. abstractive approaches. Jahan and Wijesekara (2022) even compared simple frequency-based methods (TF–IDF) with graph-based TextRank for Sinhala summarization, finding TF–IDF performed better on their limited data \cite{10}, a result that underscores the lack of sophisticated models tuned for Sinhala. A major development was the creation of the XL-Sum (multilingual summarization dataset) \cite{11} in 2021, which included a small portion of Sinhala data. Then the multimodal summarization dataset (M3LS) by Verma et al. \cite{12} provided over 10,000 Sinhala news articles with professionally curated summaries, mined from BBC Sinhala news. This dataset is by far the largest publicly available resource for Sinhala abstractive summarization. Its release enabled the training of neural summarization models for Sinhala for the first time, using architectures like mT5 or mBART that support Sinhala. Still, 10k examples is modest by deep learning standards, and they cover primarily news domain. Thus, while summarization research in Sinhala has progressed, it remains limited in breadth and robustness. There are no published Sinhala summarization systems on par with English state-of-the-art, and practical use-cases (e.g. summarizing Sinhala legal documents or literature) are left unaddressed. 
Beyond grammar and summarization, general Sinhala text corpora and pretrained models are scarce. Sinhala Wikipedia, web news archives, and publicly crawled data (e.g. Common Crawl) constitute the main sources of text. The Common Crawl-based “CC-100” \cite{13} corpus used to train multilingual models did include Sinhala, but in very small quantities relative to languages like English. For example, Conneau et al. (2020) report that the Sinhala portion of CC-100 was orders of magnitude smaller than for high-resource languages, inevitably limiting a model’s Sinhala proficiency. Indeed, the performance of multilingual language models on Sinhala correlates with the tiny training data size \cite{2}. In the absence of large monolingual corpora, researchers at University of Moratuwa recently took the initiative to compile and pre-train Sinhala-specific language models. Dhananjaya et al. (2022) trained the first substantial Sinhala monolingual BERT models (SinBERT) \cite{14} and evaluated them on Sinhala text classification. They found that prior to their work, the best available model for Sinhala was XLM-R (a multilingual RoBERTa) and even that outperformed earlier multilingual embeddings like LASER or LaBSE on Sinhala tasks. By training on a collected Sinhala corpus, their Sinhala-RoBERTa models achieved significantly better accuracy than XLM-R on classification, showing the value of tailored models. Crucially, Dhananjaya et al. also noted that research and data for Sinhala NLP are extremely scarce citing that Sinhala received very little attention in NLP literature and data resources compared to even other low-resource languages \cite{2}. The lack of publicly released datasets was a continuing problem. Looking at the work done during the past decade, mostly they have been dependent on either social media datasets or crawled news datasets. This limits the potential of Sinhala supported LLMs as SInhala is a vastly diverse language with a rich vocabulary and flow. Even when researchers create something (e.g. a corpus or tool), it is often not shared publicly, hindering others from building on it \cite{1}. There is a notable void in comprehensive text enhancement resources meaning tasks like style transfer, grammar refinement, or holistic text quality improvement have barely been explored. This sets the stage for the present research to fill these gaps by leveraging large language models in an innovative way.

\section{Perspectives from Other Low-Resource Languages}
The challenges faced in Sinhala NLP are not unique. Many low-resource languages globally share similar struggles, and examining them provides context and potential solutions. Studies on African, South Asian, and Austronesian languages (among others) reveal recurring themes: lack of corpora, absence of pretrained models, and the consequent necessity for multilingual or cross-lingual strategies. For example, languages across Africa had very limited NLP presence until the Masakhane project and others galvanized dataset creation and transfer learning approaches in recent years (Adelani et al. 2022). Similarly, in South Asia, languages like Sinhala, Nepali, and Malayalam are under-supported compared to Hindi or Bengali. A common approach has been to leverage multilingual models that include these languages in training. Multilingual transformers such as mBERT and XLM-R were trained on dozens of languages and thereby offer a starting point for low-resource cases \cite{2}. It was observed that if a language is at least included in a large multilingual model’s training, the resulting representation can be fine-tuned for decent performance on that language. Sinhala has benefited from this to some extent: inclusion in models like LASER, LaBSE, mBART, and mT5 means those models can produce Sinhala text or embeddings \cite{1} \cite{6}. However, the degree of benefit is proportional to the amount of data seen. This makes the improvement that these low-resource languages gain from fine-tuning far less significant than that seen for high-resource languages like English.
Another tactic seen in other low-resource contexts is cross-lingual transfer via a related higher-resource language. For instance, Uyghur NLP has leveraged Turkish, and Kashmiri has leveraged Hindi/Urdu \cite{16}, on the premise of lexical or structural similarity. In the case of Sinhala, one might consider whether related languages could help. Sinhala’s closest relative, Dhivehi, is also low-resource language. however, Sinhala does share some vocabulary and structure with other Indo-Aryan languages (like Bengali or even Hindi to a lesser extent). There is evidence that cross-lingual transfer can help if the model is exposed to both languages’ data during training \cite{2} \cite{17}. Many multilingual benchmarks (e.g. XTREME, MASSIVE) show that a model trained on a high-resource language can carry over some ability to a typologically similar low-resource language. In practice, direct transfer to Sinhala has limits due to script differences (Sinhala uses its own script, not Devanagari or Arabic), but techniques like transliteration or joint vocabulary training can mitigate this. A notable example in literature is the use of translation as an intermediary. When faced with a Sinhala task, one can translate the Sinhala text to English, apply an English model, and translate the output back to Sinhala. This two-step approach has been used for tasks like classification and even question answering. Ranaldi et al. (2025) refer to this as the “question-translation” approach in a multilingual QA setting \cite{18}. They found translating a low-resource language question into English before retrieval and answer generation (then translating the answer back) can improve results in some cases. However, such approaches may suffer if the translation system is weak or if the content is very culture specific. For an example an idioms may get lost in translation by taking the literal meaning like “Over the moon”. Ranaldi et al. also experimented with direct multilingual retrieval and answer generation (without translation) and a hybrid “CrossRAG” approach where retrieved documents in various languages are translated to a common language for the generator. Their findings underscore a general point. multilingual and cross-lingual methods are key for low-resource language tasks, but they must be applied carefully to handle differences in vocabulary and content coverage.
However, the global NLP community has begun initiatives specifically targeting low-resource languages. For example, Meta AI's No Language Left Behind (NLLB) project (2022) tried to collect data and train translation models for 200 languages, including Sinhala, demonstrating that, with significant effort, the resource gap can be narrowed. The NLLB model (54 billion parameters) showed improved Sinhala translation quality after incorporating newly gathered Sinhala text \cite{15}. These types of efforts usually rely on mining web data and leveraging volunteer translations, which could serve as a model for Sinhala: expanding the corpus through web crawls and OCR of books and documents, and then training models on the result. Another example is the Indic NLP Library and AI4Bharat efforts which focused on Indian languages. While Sinhala is not an official Indian language, these projects improved tooling for languages like Tamil and Sinhala through shared efforts (e.g. cross-lingual word embeddings). From these global perspectives, a few trends are clear: (1) Resource creation (even if small) is critical. Any new dataset can support research if shared. (2) Multilingual pretraining is a strong foundation. Utilizing models like XLM-R or mT5 is now standard practice to give low-resource languages a fighting chance \cite{2}. (3) Adaptive techniques such as transfer learning, fine-tuning with small data, and data augmentation are commonly employed to compensate for data shortages. The experiences from other low-resource languages provide a blueprint: despite the challenges, methods exist to elevate a low-resource language's NLP capabilities by creatively utilizing whatever resources are available and by borrowing strength from high-resource languages. These insights reinforce the chosen direction for Sinhala—using whatever limited data and resources are available in creative ways to improve support for the language.


\section{Approaches to Improving LLM Support for Low-Resource Languages}
Given the limitations in datasets and pretrained models for Sinhala, researchers have explored a variety of techniques to improve this. Multilingual and cross lingual training, prompt based learning (few shot prompting), data augmentation, cross lingual transfer learning, parameter efficient fine tuning are some of these methods highlighted in the recent past. Let’s dive into these concepts and their potential one by one.

\subsection{Multilingual Pretraining and Cross-Lingual Transfer}
Multilingual pretraining has been a game changer for low-resource languages in NLP. Models like mBERT, XLM-R, mT5, and mBART have been trained on text from hundreds of languages, including low-resource ones. The idea is that a model with a shared vocabulary and parameters for multiple languages can transfer knowledge among them. For instance, a concept learned in one language might help the model understand the same concept expressed in another language. For Sinhala, multilingual transformers offered the first real high-performance encoders/decoders – e.g., XLM-R’s strong results on Sinhala text classification \cite{2}. However, this performance is limited by the amount of Sinhala used in pretraining. This is still better than nothing, since even a small amount of Sinhala text embedded in a massive model enables zero-shot or few-shot capabilities that were previously impossible. For example, an instruction-tuned multilingual model (like Google’s FLAN-T5 or Facebook’s XGLM) can often understand basic Sinhala prompts and generate Sinhala output, despite never being explicitly trained for Sinhala tasks. But this ability is far from perfect, as this can lead to many grammatical errors. Recent studies have quantified this cross-lingual ability. Cahyawijaya et al. (2024) show that large models are indeed “few-shot in-context learners” even for low-resource languages \cite{2}. By supplying a few examples in the target language, an LLM like GPT-3 can perform tasks in languages it has minimal training data for \cite{17}. Their extensive study over 25 low-resource languages finds that in-context learning narrows the gap by leveraging the model’s latent multilingual knowledge, especially when the examples help align the semantics between the low-resource language and a language the model knows well.
This cross-lingual alignment strategy – sometimes called X-ICL(cross-lingual in-context learning) \cite{20} can significantly improve performance on low-resource tasks by essentially guiding the model to transfer what it knows from a high-resource language to the low-resource context. For example if given a paragraph to summarize in Sinhala, we can provide couple of examples of good English summaries, the model has the ability to apply the learned task to Sinhala. According to studies, a carefully curated prompt design can yield better results.
multilingual models combined with cross-lingual prompting or fine-tuning allow knowledge transfer from high-resource to low-resource languages, offering a powerful approach to compensate for limited data. This insight underpins our thesis methodology. We exploit the fact that modern LLMs (like GPT-4 or multilingual transformers) have some latent Sinhala ability that can be activated and improved through cross-lingual context and fine-tuning.

\subsection{Data Augmentation and Synthetic Data Generation}
When real data is scarce, creating synthetic data is a well-established approach. In machine translation, back-translation \cite{21} is a classic example that translates target-language sentences to the source language to augment parallel data. Similar ideas have been applied to other tasks and languages. For Sinhala, data augmentation has been used to resolve problems like out-of-vocabulary (OOV) words and domain adaptation in translation. For example, Fernando et al. (2020) \cite{22} explored augmenting a Sinhala-English-Tamil translation model by generating synthetic parallel sentences for domain-specific terms. This study presented two augmentation techniques to generate synthetic Sinhala sentences and demonstrated that these techniques improved translation of sentences containing OOV terms. Furthermore, this study shows the model could better handle rare words by injecting semantically plausible fake sentences into training. They constrained the synthetic data with semantic and syntactic checks to maintain fluency \cite{21}. The results showed that even simple semantic constraints (e.g. using word embeddings to ensure replacements make sense) can significantly help, which the authors highlight as “promising for low-resource languages that have limited linguistic tool support”. In other words, even without a perfect parser or extensive lexicons, we can leverage word vectors from a monolingual corpus to create useful new examples, a practical trick in low-resource settings.
For tasks like grammatical error correction (GEC), data augmentation is often done by generating artificial errors in correct sentences. In absence of a Sinhala error corpus, a system could take clean Sinhala text and algorithmically insert errors (spelling mistakes, agreement errors, etc.) to train a correction model. This approach has worked for low-resource GEC in other languages (e.g. Russian, Ukrainian). Although we did not find a specific publication for Sinhala GEC augmentation, the concept is acknowledged in Jayasuriya et al. (2023) that creating even a synthetic error corpus is a needed step for Sinhala \cite{5}. Likewise, for summarization, one could augment data by paraphrasing or using translation. For example,  take an English article, translate it to Sinhala (to serve as “input”), and translate its summary to Sinhala (to serve as “output”). This effectively generates a Sinhala summarization pair using a pivot language. The risk with synthetic data is that it may not fully capture the nuances of the target language, but it undeniably expands the training material. Given Sinhala’s low-resource status, augmentation is not just helpful but perhaps necessary to get sufficient training examples for any deep learning model. Our literature review supports incorporating data augmentation in the thesis: whether by using translation-based techniques, noising and denoising tasks, or retrieval of related sentences to form new training pairs, these methods can supply the model with much-needed exposure to Sinhala text variations. In summary, data augmentation offers a way to amplify low-resource datasets, and when guided by linguistic constraints or high-resource references, it can improve model robustness in Sinhala \cite{22}.

\subsection{Prompt Engineering and Few-Shot Learning}
Prompt engineering refers to designing sophisticated inputs to an LLM that instructs it to perform a task without additional training. This includes formulating instructions, providing a role or context, and giving examples in the prompt (few-shot prompting). In low-resource scenarios, prompt engineering is appealing because it does not require training data or model updates – instead, it leverages the knowledge already present in a large model. Many recent works have explored the efficacy of prompt-based vs fine-tuned approaches. A relevant study by Trad and Chehab \cite{23} compared prompt engineering with fine-tuning for a niche task (phishing URL detection) across GPT-3.5, Claude, and fine-tunable models. They tried various prompt strategies (zero-shot instructions, role-playing scenarios, and even chain-of-thought reasoning) and managed to get an F1 score close to 92.7\% with an optimized prompt on GPT-3.5. This shows that a carefully engineered prompt can indeed achieve high performance, equivalent to complex feature-based classifiers. However, when they fine-tuned smaller LMs (GPT-2, DistilGPT-2, etc.) on a small phishing dataset, they reached even higher performance (around 97\% F1). Moreover, in more realistic settings and edge cases, the fine-tuned models proved more robust than prompt-only solutions. The authors concluded that while prompt engineering allows rapid prototyping without training, fine-tuning for the specific task ultimately yields superior accuracy, and they suggest hybrid strategies (using prompt-engineered data to assist fine-tuning, etc.). This finding is echoed in other literature that prompts can get you surprisingly far, but there is often a gap that only task-specific adaptation can fill.
For Sinhala and other low-resource languages, prompt engineering might involve instructing the model in English but asking for Sinhala output, or providing example pairs in Sinhala (few-shot). For example, one could show a GPT-4 model two examples of “informal Sinhala sentence -> formal corrected Sinhala sentence” and then ask it to do the same for a new input. If GPT-4’s multilingual training is decent, it may follow the pattern and produce a corrected formal sentence. This is essentially using few-shot learning as a way to do style transfer or error correction. Research by Cahyawijaya et al. (2023) \cite{24} indeed confirms that few-shot prompts can significantly enhance a model’s performance in low resources languages, by bridging the task understanding from higher-resource languages. However, one must carefully choose how to present the examples. An interesting point from their work was that naïvely mixing languages in the prompt (e.g. giving an English example for a Sinhala task) can confuse the model unless handled properly. They found that aligning the query (i.e., making the model see the task in the same language space as it will output) was more effective than just aligning labels. In practice, this might mean translating any English instructions to Sinhala so the model fully operates in Sinhala for that query. But this does not mean using a low-resource language for querying will always work. For instance, Ranaldi et al. (2025) tried prompting a model to retrieve answers in multilingual QA by either giving the question in English or the native language. Their translation-following method effectively prompted-engineered the retrieval step and improved coverage for low-resource languages. So, this implies that the prompting language will ultimately depend on multiple variables such as the task, the quality of examples etc, for the model to perform better.

In summary, prompt engineering is a game-changer for low-resource NLP, especially for languages like Sinhala, because it lets us leverage large language models that have already seen some Sinhala text, even if we don’t have extensive labeled data. It’s particularly helpful for structured tasks or stylistic changes, such as writing letters or correcting grammar, because we can clearly instruct the model on exactly what kind of output we want.
However, as researchers have noted, prompt-based responses can sometimes be inconsistent or break down when the input differs significantly from examples provided in the prompts. To address this, this thesis suggests combining prompting with techniques like retrieval and minimal fine-tuning, combining their strengths to create more reliable outcomes.
Yet, even without any training examples, the zero-shot and few-shot capabilities of large language models enable us to tackle tasks simply by phrasing requests thoughtfully. This marks a significant shift away from traditional methods that heavily relied on supervised training data, and it’s particularly meaningful in contexts like Sinhala NLP, where resources are limited.

\subsection{Parameter-Efficient Fine-Tuning (Adapters and LoRA)}
While prompt engineering works at inference time, fine-tuning modifies the model itself to better handle a task or language. Traditional fine-tuning (updating all model weights) is often infeasible with today’s large models, especially for researchers with limited hardware and resources. This has led to parameter-efficient fine-tuning (PEFT) methods like adapters and LoRA (Low-Rank Adaptation), which update only a small fraction of the model’s parameters. The idea is to inject a small trainable module or tweak into the network that can be learned with limited data and compute, while the vast majority of the model’s knowledge is frozen. Adapters (Houlsby et al. 2019) \cite{25} add tiny bottleneck layers to each transformer block. LoRA (Hu et al. 2021) \cite{26} inserts low-rank weight matrices that are trained instead of the full weights. These techniques have shown they can fine-tune massive models with minimal GPU memory and without overfitting to small datasets. For example, recent research introduced LOMO (Low-Memory Optimization), a fine-tuning regimen that combines gradient checkpointing and quantization to enable full fine-tuning of a 65B model on limited hardware. But even without full fine-tuning, approaches like LoRA have been embraced in community projects to adapt models like LLaMA-2 for new languages. Indeed, there have been community-driven efforts to create a “Sinhala LLaMA” by fine-tuning LLaMA on whatever Sinhala text is available, often using LoRA for practicality (some are visible on HuggingFace Hub \cite{10}). These LoRA-adapted models are typically small (e.g. a GPT-Neo 125M fine-tuned on Sinhala Wikipedia) and far from the power of GPT-3, but they represent important steps. Dhananjaya et al. (2022) \cite{2} also effectively did a form of PEFT by training Sinhala RoBERTa models from scratch on a limited corpus and then fine-tuning them on downstream tasks Their approach of releasing the models and some new datasets was a boost for Sinhala NLP research. Furthermore, a study by Rathnayake et al. (2023) \cite{27} used adapter-based fine-tuning on XLM-R to handle Sinhala-English code-mixed text classification. By plugging in adapters for Sinhala, they could specialize a multilingual model to that mixed language scenario without retraining everything. This demonstrates the versatility of parameter-efficient methods in low-resource setups: one can add new capabilities to a model with relatively few parameters tuned.
The literature suggests that even a small amount of fine-tuning data can noticeably improve an LLM’s performance in a low-resource language, which aligns with our intuition. The critical takeaway from the literature is that PEFT techniques are enabling low-resource communities to customize large models to their languages/tasks without needing enormous data or compute.

\subsection{Retrieval-Augmented Generation (RAG)}
Retrieval-Augmented Generation (RAG) is a method that combines an information retrieval component with a text generator to enhance the generator’s performance, especially on knowledge-intensive tasks. The core idea, introduced by Lewis et al. (2020) \cite{28}, is that instead of relying solely on the model’s internal knowledge (which might be incomplete or outdated), we can fetch relevant external documents and feed them into the model as context for generation. This approach has two major benefits. It mitigates hallucinations (the model can base its output on real retrieved facts) and it injects up-to-date or domain-specific information that the model wasn’t trained on. While RAG was initially popularized for open-domain question answering, it has rapidly become a cornerstone technique in many NLP applications, from conversational agents (e.g. Bing Chat retrieving web results) to personalized assistants.
In multilingual and low-resource contexts, RAG is particularly appealing. If a model doesn’t know much about a topic in Sinhala, we can compensate by retrieving documents in Sinhala about that topic from a local corpus or knowledge base. RAG thus offers a way to circumvent the lack of training data: instead of trying to bake all of Sinhala knowledge into the model’s weights, we let the model look things up as needed. Ranaldi et al. (2025) \cite{18} explicitly investigate RAG for multiple languages and highlight that its use in multilingual settings was previously underexplored. They implement variants where either the query or the retrieved documents are translated to English, versus a fully multilingual retrieval mode. One interesting finding was that a naive multilingual RAG (where the question is asked in, say, Sinhala and documents are retrieved from a Sinhala wiki) can suffer if the document corpus is sparse, whereas translating the question to English to tap into English Wikipedia yields more hits but then creates a disconnect for generation. Their proposed solution, CrossRAG, translates retrieved foreign-language documents into English before giving them to the generator. This way, the generator (which might be stronger in English) processes everything in one language and produces an answer, which can then be translated back. This method significantly improved QA performance for both high and low-resource languages in their experiments. 
For our purposes, RAG is attractive not for QA per se but for text generation tasks like letter writing. The principle remains: provide the model with relevant text snippets so it has concrete material to base the output on. In the case of formal letter generation, we can build a knowledge base of existing official letters (e.g. a database of letters categorized by type: job applications, complaint letters, invitations, etc.). When the user requests a certain type of letter, the system can retrieve a few similar letters or even specific phrases from this database. These retrieved pieces then serve as in-context examples or guides for the LLM. By seeing actual examples of formal phrasing, structuring, correct salutations, closings, and domain-specific terminology, the LLM is far more likely to produce a correct and contextually appropriate letter. This approach addresses two issues identified in the literature. The lack of training data (we might have too few example letters to fully fine-tune a model, but we can still use those examples at inference via retrieval) and the tendency of models to hallucinate on limited data.(The retrieved text grounds the generation in real content, reducing guesswork). Moreover, RAG aligns with the general direction of making LLM outputs verifiable and traceable – the retrieved documents can act as evidence or at least inspiration, which is useful in formal writing where factual correctness and appropriate references matter.

\section{Multilingual Large Language Models for Low-Resource Languages}
The emergence of large-scale multilingual language models has created new opportunities for low-resource language processing. Models specifically designed with extensive multilingual capabilities have shown promising results for languages like Sinhala, which traditionally suffer from limited training data and resources. This section examines state-of-the-art multilingual LLMs, with particular focus on models suitable for Sinhala text generation.

Among recent developments, several multilingual LLMs have demonstrated varying degrees of effectiveness for low-resource languages. Models such as BLOOM (BigScience Large Open-science Open-access Multilingual Language Model), which supports 46 languages and 13 programming languages \cite{30}, and Meta's LLaMA series have been widely adopted by the research community. However, these models often prioritize high-resource languages in their training distribution, leading to suboptimal performance on languages like Sinhala. The mT5 (multilingual Text-to-Text Transfer Transformer) and mBART models, while supporting over 100 languages, similarly exhibit performance degradation for extremely low-resource languages due to limited exposure during pretraining \cite{2}.

A significant advancement came with Cohere's Aya initiative, which aimed to support massively multilingual text generation for underrepresented languages. The initiative released two relevant model families. Aya-101 is a 13-billion-parameter model covering 101 languages, including Sinhala, and is therefore directly relevant to Sinhala text generation \cite{31}. The later Aya-23 family (8B and 35B parameters) achieves stronger per-language quality but covers a smaller set of 23 higher-resource languages, which does not include Sinhala. The 8B Aya-23 variant (approximately 4.8\,GB when 4-bit quantized, with an 8192-token context window) is nonetheless attractive for local, offline deployment via the Ollama framework. Unlike general-purpose multilingual models that treat low-resource languages as an afterthought, the Aya initiative specifically aimed to collect high-quality data for underrepresented languages through a global collaborative effort involving native speakers. This focused, community-driven data collection is intended to give Aya models a stronger grounding in the syntax, morphology, and cultural context of underrepresented languages than is typically obtained from incidental web-crawled coverage in larger general-purpose models.

When selecting an LLM for this research, several alternatives were evaluated:

\textbf{GPT-4 and GPT-3.5 (OpenAI):} While these models demonstrate strong general capabilities and have some Sinhala knowledge from web-crawled data, they suffer from three critical limitations for this research: (1) they require expensive API calls, making them unsuitable for deployment in resource-constrained environments; (2) their Sinhala capabilities are inconsistent, often mixing colloquial and formal registers inappropriately; and (3) they cannot be deployed locally, creating dependency on external services and raising data privacy concerns for formal letter generation.

\textbf{LLaMA 3.2:3b and LLaMA 2 variants:} Meta's LLaMA models, particularly the smaller 3-billion parameter variant, offer the advantage of local deployment through frameworks like Ollama. However, initial experiments revealed severe limitations in Sinhala information extraction. When prompted to extract structured information from Sinhala text (e.g., letter type, recipient, subject), LLaMA 3.2:3b consistently returned field descriptions rather than actual extracted values, indicating insufficient Sinhala language understanding despite its multilingual pretraining \cite{32}.

\textbf{mT5 and mBART:} These encoder-decoder models support Sinhala and have been used successfully for translation and summarization tasks \cite{11}. However, for generative tasks requiring both information extraction and formal letter composition, their performance on Sinhala was found to be inconsistent, particularly for complex honorific structures and formal register requirements. Additionally, their maximum context length limitations (typically 512-1024 tokens) pose challenges for RAG applications where multiple retrieved examples must be included in the prompt.

\textbf{XGLM and BLOOM:} While BLOOM's 176B parameter variant shows reasonable multilingual capabilities, its computational requirements (requiring multiple high-end GPUs) make it impractical for deployment in typical research or production environments. XGLM, despite supporting Sinhala, exhibited similar extraction quality issues as smaller LLaMA variants.

\textbf{Aya (Aya-101 and Aya-23 8B):} The Aya models present several relevant characteristics for Sinhala text generation research:

\begin{itemize}
    \item \textbf{Sinhala coverage:} Aya-101 was trained through a global, community-driven effort on a curated multilingual dataset covering 101 languages including Sinhala, giving it explicit Sinhala support that most general-purpose models lack. The lighter 8B Aya-23 variant does not officially list Sinhala among its 23 languages, but is retained as a practical local-deployment option whose Sinhala behaviour can be supplemented by the retrieval-augmented context provided by the pipeline.

    \item \textbf{Extraction quality:} Its instruction-following ability and Sinhala-inclusive training make Aya 8B a strong candidate for extracting structured information from informal Sinhala prompts, including letter types ({\sinhalafont ඉල්ලීම්, පැමිණිලි, ස්තූති}), recipients, subjects, and purposes—a task where smaller models such as LLaMA 3.2:3b consistently failed in initial testing.

    \item \textbf{Local deployment:} Aya 8B can be deployed locally using the Ollama inference framework, which is relevant for scenarios where data privacy or offline operation is required.

    \item \textbf{Generation quality:} Aya 8B is designed to maintain formal Sinhala register ({\sinhalafont ලිඛිත භාෂාව}), apply honorific verb forms based on context, and structure letters according to conventional Sinhala formal letter templates, making it a suitable local-deployment alternative for the generation step.

    \item \textbf{Context window:} Aya 8B supports an 8192-token context window, sufficient for incorporating multiple retrieved letter examples in the RAG pipeline along with extraction results and generation instructions.
\end{itemize}

A key design decision in this research is that the pipeline does \textit{not} commit to a single LLM. Instead, the system implements a provider-agnostic LLM factory (described in detail in Chapter 4) that supports multiple model providers—including Ollama-hosted models such as Aya 8B, Google Gemini, OpenAI, Azure OpenAI, and HuggingFace models—through a unified configuration interface. This means the RAG pipeline's effectiveness can be evaluated with different underlying models, and the research findings apply to the retrieval and augmentation approach rather than to any specific LLM. The model layer is deliberately decoupled from the rest of the pipeline, enabling reproducibility across different hardware and deployment environments.

\subsection{Categories of Sinhala Formal Letters}
Formal Sinhala letters can be categorized into several distinct types, each with specific purposes and slightly different conventions. Understanding these categories is essential for generating contextually appropriate letters, as each type has characteristic vocabulary, tone, and structural variations. The main categories include:

\begin{enumerate}
    \item Request Letters ({\sinhalafont ඉල්ලීම් ලිපි}) - Used to formally request information, permissions, resources, or actions from authorities or institutions.
    \item Invitation Letters ({\sinhalafont ආරාධනා ලිපි}) - Formal invitations to events, ceremonies, or meetings.
    \item Thank You Letters ({\sinhalafont ස්තූති ලිපි}) - Expressing formal gratitude for assistance, support, or participation.
    \item Recommendation Letters ({\sinhalafont නිර්දේශ ලිපි}) - Providing formal recommendations for individuals for employment, education, or other purposes.
    \item Inquiry Letters ({\sinhalafont විචාරණ ලිපි}) - Seeking information or clarification on specific matters.
    \item Transfer Letters ({\sinhalafont මාරු ලිපි}) - Requesting or notifying transfers of position, location, or responsibility.
    \item Leave Letters ({\sinhalafont නිවාඩු ලිපි}) - Formally requesting time off from work or educational institutions.
    \item Complaint Letters ({\sinhalafont පැමිණිලි ලිපි}) - Lodging formal complaints about services, conduct, or situations.
    \item Apology Letters ({\sinhalafont සමාව ඉල්ලීමේ ලිපි}) - Offering formal apologies for mistakes, delays, or misconduct.
\end{enumerate}

\subsection{Challenges in Formal Sinhala Letter Generation}
While the aforementioned techniques and models provide a foundation for Sinhala NLP, generating formal Sinhala letters presents unique challenges that intersect linguistic complexity, cultural conventions, and technical limitations. Understanding these challenges is essential for designing an effective RAG-based system.

\subsubsection{Morphological Complexity}
Sinhala is a morphologically rich language with complex inflectional patterns. Words in Sinhala change their form based on case, number, tense, gender, honorific level, and grammatical function, creating significant challenges for language models. Unlike English, where word forms are relatively stable, Sinhala verbs can take dozens of different forms depending on tense, aspect, mood, and politeness level. For instance, the verb "to go" (යනවා) has distinct forms for different contexts: යන්න (infinitive), ගියා (past informal), ගියේය (past formal/written), යති (literary present), and many others. Similarly, nouns decline based on case and number, with different declension patterns for animate and inanimate objects. This morphological richness means that LLMs must not only select appropriate vocabulary but also generate the correct inflected forms, which requires deep understanding of Sinhala grammar – knowledge that is often lacking in models trained primarily on high-resource languages.

\subsubsection{Honorifics and Register}
Formal Sinhala letter writing demands careful attention to honorifics and linguistic register, which reflect the social relationship between sender and recipient. Sinhala has distinct honorific systems encoded in verb forms, pronouns, and noun declensions. For example, addressing a superior requires using honorific verbs (පිළිතුරු දෙන්න vs. පිළිතුරු දෙනවා), respectful pronouns (ඔබතුමා vs. ඔයා), and formal noun forms (ලිපිය vs. පොත). The choice of honorific level depends on multiple factors: the recipient's social status, professional relationship, institutional context, and the letter's purpose. A job application to a principal requires very high honorifics (ඉතා ගෞරවනීය), while a request to a peer organization uses moderate formality. Furthermore, formal written Sinhala (ලිඛිත භාෂාව) differs substantially from spoken Sinhala (කථන භාෂාව), employing distinct vocabulary, verb forms, and sentence structures. LLMs must navigate these sociolinguistic nuances to produce contextually appropriate letters – a task requiring sophisticated pragmatic understanding beyond syntactic correctness.

\subsubsection{Limited Digital Corpus}
A fundamental challenge is the scarcity of digitized Sinhala formal letters compared to high-resource languages. While English has vast corpora of business correspondence, legal documents, and formal writing available for training, Sinhala formal letters exist primarily in physical archives in government offices, schools, and institutions. This data scarcity has multiple implications: (1) LLMs have minimal exposure to formal Sinhala letter structures during pretraining, leading to poor zero-shot performance; (2) fine-tuning approaches are constrained by lack of training examples; and (3) without sufficient data, models cannot learn the conventional phrases, templates, and structural patterns that characterize different letter types. Even when digital Sinhala text exists (e.g., news articles, social media, Wikipedia), it predominantly represents informal or journalistic registers rather than the highly formal administrative language required for official correspondence. This domain mismatch further limits the utility of general Sinhala corpora for formal letter generation.

\subsubsection{Diglossia}
Sinhala exhibits strong diglossia, with significant structural and lexical differences between formal written Sinhala and colloquial spoken Sinhala. This diglossic variation extends beyond simple register differences; the written and spoken forms use different vocabulary sets, distinct grammatical constructions, and even different verb paradigms. For example, the spoken Sinhala phrase "මම කාලා" (I ate) becomes "මම කෑවෙමි" or "අනුභව කළෙමි" in formal written contexts. Many common spoken words have completely different formal equivalents: spoken "දැන්" (now) becomes written "දැන්"; spoken "කොහාද" (where) becomes written "කොතැනද" or "කවරස්ථානයේද" in very formal contexts. LLMs trained primarily on web-crawled Sinhala data tend to produce colloquial forms even when formal register is required, because spoken Sinhala dominates social media and online forums. Successfully generating formal letters requires the model to consistently maintain written register throughout the document, applying the appropriate verb forms, vocabulary, and sentence structures – a challenging code-switching task that many multilingual models perform poorly.

These linguistic and resource-based challenges motivate the retrieval-augmented approach adopted in this research. By retrieving actual formal letter examples that demonstrate correct morphology, appropriate honorifics, and proper written register, the RAG system can ground the LLM's generation in concrete exemplars, compensating for its limited Sinhala training and helping bridge the gap between the model's predominantly informal Sinhala knowledge and the formal writing requirements of official correspondence.

\chapter{Methodology}
This chapter describes the methodology used to design, construct, and evaluate the proposed Retrieval-Augmented Generation (RAG) approach for formal Sinhala letter generation. The methodology follows a design science research process: first identifying the limitations of general-purpose LLMs for Sinhala formal writing, then constructing an artifact that combines a curated Sinhala letter corpus, semantic retrieval, information extraction, prompt augmentation, and model-agnostic text generation. The resulting system is evaluated by comparing its output against a non-RAG LLM baseline using expert judgement.

\section{Research Design}
This section presents the research design, including the assumptions made during system construction, the RAG pipeline followed by the proposed system, the datasets used to build the knowledge base, the preprocessing steps applied to the data, and the methods used for retrieval and generation.

\subsection{Design Assumptions}
The statements mentioned below are assumed to be true by the researchers with regard to the research design.

\begin{itemize}
    \item The research design approach considered government letters provided by the University of Moratuwa and the dataset created by the authors.
    \item Users or evaluators will provide prompts that contain at least the core intent of the letter, even if some supporting details are missing.
    \item General-purpose multilingual LLMs contain partial knowledge of formal letter templates and Sinhala writing conventions, but this knowledge is insufficient for consistently producing structurally correct and contextually appropriate formal Sinhala letters without additional grounding.
    \item A curated Sinhala letter corpus can provide useful structural and stylistic examples that compensate for the limited Sinhala-specific knowledge available in general-purpose LLMs.
    \item Human expert evaluation is necessary for assessing grammar, formal register, cultural appropriateness, and structural correctness, as automated NLG metrics alone cannot reliably capture the quality of formal Sinhala writing.
\end{itemize}

\subsection{Retrieval-Augmented Generation Pipeline}
The proposed method uses Retrieval-Augmented Generation to ground the LLM in examples of formal Sinhala writing before generating the final letter. Instead of sending the user's prompt directly to the LLM, the system first converts the prompt into structured metadata, retrieves relevant letter structures and examples from a Sinhala knowledge base, and constructs an enhanced prompt containing both the user requirement and retrieved context.

The methodology follows five main stages:

\begin{enumerate}
    \item \textbf{Information Extraction:} The user prompt is analysed to identify the letter type, recipient, sender, subject, purpose, and supporting details. A transformer-based XLM-RoBERTa NER model is used for structured extraction, while an LLM-based extractor is used as a backup strategy for prompts where the NER model fails to identify all required fields or where the user input is highly informal.
    \item \textbf{Gap Detection:} The extracted fields are checked against the minimum information required for the identified letter type. If mandatory fields are missing, the system asks clarification questions in Sinhala before continuing.
    \item \textbf{Retrieval:} The extracted metadata is converted into a Sinhala-aware semantic query. FAISS retrieves candidate documents from the indexed Sinhala letter corpus, including one structure template and relevant example letters.
    \item \textbf{Reranking and Prompt Construction:} Retrieved examples are reranked using a cross-encoder to improve relevance. The final context is combined with the original prompt and extracted fields to form an enhanced prompt.
    \item \textbf{Letter Generation:} The enhanced prompt is passed to the configured LLM to generate a complete formal Sinhala letter. The generated output can later be reviewed and rated by users or evaluators.
\end{enumerate}

This pipeline directly addresses the low-resource nature of Sinhala by shifting part of the burden from the model's internal parameters to an external, curated, domain-specific knowledge base. \section{Pilot Project: Formal Letter Generation in Sinhala}
This research study specifically targets the improvement of Sinhala text generation in LLMs through a more focused study of formal Sinhala letter writing.

Formal Sinhala letters are a significant part of written communication in Sri Lanka, in government, educational institutions, and other sectors. These letters follow a strict structure and a formal writing style (written language, {\sinhalafont ලිඛිත භාෂාව}), and the writer must have a thorough command of the orthography ({\sinhalafont අක්ෂර වින්‍යාසය})—the set of standards that should be followed, including spelling rules, punctuation, and letter formation. It is equally important that these letters follow the relevant grammar conventions. Formal letter writing is also a crucial skill in the Sri Lankan education system, and is still examined in the Ordinary Level Sinhala examination paper.

\section{Data Sources}
\subsection{Data Acquisition}
The dataset in this research was acquired through three approaches to ensure comprehensive coverage of formal letters and to avoid bias in creating the dataset.

\begin{enumerate}
    \item First, we reviewed the past Sinhala Language and Literature GCE Ordinary Level Examination papers from year 2011 - 2025, model papers for Sinhala, and Sinhala Language and Literature papers for Grade 10 and Grade 11 from different provinces and schools from which we identified the formal letter writing questions. The identified questions were digitized using an OCR-enabled scanning API because many of the papers were available either as printed documents or as scanned image-based PDF files from which text could not be directly extracted. The converted data were then stored in the structured CSV format used by the knowledge base.
    \item Secondly, we collected formal letter prompts/questions from online resources, and other model papers and distributed the questions among a group of students who have successfully passed the GCE O/L examination with A passes for Sinhala Language and Literature. They were then asked to write formal letters for the given prompts and they were then entered to the dataset to make this more authentic. 
    \item Finally, aiming to capture real-world examples, we obtained formal letters sent from and to government institutions, banks, schools, professional bodies, and members of the public. The larger raw collection was reviewed and filtered, and 150 high-quality curated letters were selected for the final retrieval corpus. The dataset received from the University of Moratuwa was already digitized and available as text files, while the letters obtained through personal contacts were digitized using OCR before being converted into the same CSV schema.
\end{enumerate}

\section{Data Preprocessing}
The collected dataset was pre-processed to make it suitable for embedding, retrieval, and prompt construction. The goal of preprocessing was not to rewrite the letters, but to remove irrelevant noise, preserve useful formal writing patterns, and represent each document using a consistent schema.

\subsection{Removing lengthy letters}
The letter contents with more than 150 words were manually removed from the dataset. These texts were challenging to deal with and such letters made the model deviate from what was expected as output. Some of these lengthy letters included a copy of former letters sent, forms to fill and name lists and their descriptions. 

\subsection{Removing Non-Essential Components manually}
The goal here was to maintain a standardized structure, to remove the personal details such as addresses from the collected letters from institutions and personal contacts, and to remove the obvious components like Salutations and Closing remarks. The final contents of the CSV only had the subject and the main body of the letter, as illustrated in Figure \ref{fig:letter_transform}. Removed elements included the following.

\begin{itemize}
    \item Sender Address
    \item Recipient Address
    \item Date
    \item Salutation
    \item Closing remarks
    \item Signature blocks
\end{itemize}

The corpus contains both complete letter examples and structure templates so that retrieval can provide the LLM with both content-level examples and format-level guidance.

\section{Technology Stack}

\subsection{Text Embedding}

\subsubsection{LaBSE}
LaBSE is a Language-agnostic BERT sentence embedding model designed to produce sentence-level representations across more than one hundred languages. This model encodes text into high-dimensional vectors and was originally trained for cross-lingual sentence alignment. However, its usages extend beyond translation, enabling semantic similarity search, clustering, and retrieval across languages.

In this research, LaBSE is used to create embeddings for Sinhala letter examples, structure templates, and user-derived search queries. The main reason for selecting LaBSE is that it can represent Sinhala text in a multilingual semantic vector space without requiring a Sinhala-specific embedding model to be trained from scratch. This is particularly useful for low-resource language settings where large monolingual embedding datasets are not available.

\subsection{Semantic Retrieval}

\subsubsection{FAISS Index}

FAISS (Facebook AI Similarity Search) is a library developed by Meta AI Research for efficient similarity search and clustering of dense vectors \cite{johnson2019billion}. Written in C++ with complete Python wrappers, FAISS implements optimized algorithms for searching in large-scale vector datasets, making it ideal for retrieval-augmented generation systems.

\textbf{Selection Rationale:}

FAISS was selected over alternative vector databases (Pinecone, Weaviate, ChromaDB) for several design considerations:

\begin{itemize}
    \item \textbf{Offline Operation:} FAISS operates entirely locally without requiring external API connections, ensuring reproducibility and eliminating dependency on third-party services
    \item \textbf{Simplicity:} For a research corpus of 150 documents, FAISS provides sufficient functionality without the overhead of distributed vector databases
    \item \textbf{Performance:} Optimized C++ implementation with SIMD operations enables sub-millisecond search latency even on CPU-only hardware
    \item \textbf{Language Agnostic:} FAISS operates on numerical vectors, making it suitable for any language including low-resource Sinhala
\end{itemize}

\textbf{Architecture and Workflow:}

The FAISS-based retrieval system follows a two-phase architecture:

\textbf{Phase 1 - Indexing (Offline):}
\begin{enumerate}
    \item The cleaned Sinhala letter corpus is loaded from the CSV knowledge base.
    \item Each row is converted into a document consisting of the title, content, and metadata fields such as letter category, document type, register, source, tags, and rating.
    \item Long documents are split into overlapping chunks so that each indexed unit remains within a suitable retrieval length.
    \item Each chunk is embedded using LaBSE.
    \item The resulting vectors are stored in a FAISS vector index and persisted locally so that the index can be reused without rebuilding it for every application run.
\end{enumerate}

\textbf{Phase 2 - Retrieval (Online):}
\begin{enumerate}
    \item The extracted user intent is converted into a Sinhala-aware retrieval query using the letter type, subject, purpose, and details.
    \item The query is embedded using the same LaBSE model used during indexing.
    \item FAISS performs similarity search to retrieve candidate documents from the vector index.
    \item Retrieved candidates are filtered using metadata such as \texttt{letter\_category} and \texttt{doc\_type}, allowing the system to separately retrieve a structure template and example letters.
    \item The selected examples are passed to the reranking stage for precision refinement before prompt construction.
\end{enumerate}

\textbf{Index Configuration:}

The system uses FAISS through the LangChain vector store interface. For the scale of this research corpus, exact similarity search is sufficient and avoids the additional configuration complexity of approximate indexes. While approximate methods such as IVF or HNSW would be useful for very large corpora, the current corpus size allows the system to prioritize deterministic retrieval and simple reproducibility.

This indexing method provides:
\begin{itemize}
    \item local operation without external vector database dependencies,
    \item persistent storage of the FAISS index for reuse,
    \item metadata-aware retrieval of structure templates and examples, and
    \item sufficient retrieval speed for an interactive letter generation workflow.
\end{itemize}

This design enables rapid prototyping while maintaining the flexibility to scale to larger corpora using approximate indexing methods in future work.

\subsubsection{Cross-Encoder Reranking}

While FAISS provides efficient initial retrieval through embedding similarity, it suffers from a fundamental limitation of bi-encoder architectures: queries and documents are encoded independently, limiting the model's ability to capture fine-grained semantic interactions between them. To address this, the system implements a two-stage retrieval pipeline where FAISS handles fast candidate generation (Stage 1) and a cross-encoder performs precise relevance scoring (Stage 2).

\textbf{Two-Stage Retrieval Design:}

\textbf{Stage 1 - Bi-Encoder Retrieval (FAISS):}
\begin{itemize}
    \item Encodes query and documents separately using LaBSE
    \item Computes similarity through vector distance metrics
    \item Fast but semantically limited (cannot model query-document interactions)
    \item Retrieves a candidate set of structure templates and examples from the indexed corpus
\end{itemize}

\textbf{Stage 2 - Cross-Encoder Reranking:}
\begin{itemize}
    \item Encodes query and document together as a single concatenated sequence
    \item Attention mechanism models interactions between query and document tokens
    \item Produces a relevance score for each (query, document) pair
    \item Reranks the candidate examples and selects the most relevant ones for prompt construction
\end{itemize}

\textbf{Model Selection:}

The cross-encoder model \texttt{cross-encoder/ms-marco-MiniLM-L-6-v2} was selected based on:
\begin{itemize}
    \item \textbf{Compact Architecture:} 6-layer MiniLM (22.7M parameters) balances accuracy and inference speed
    \item \textbf{Ranking Specialization:} Trained on MS MARCO passage ranking dataset for relevance scoring
    \item \textbf{Practical Zero-Shot Use:} Although it is not trained specifically for Sinhala formal letters, it provides a lightweight reranking mechanism suitable for comparing semantically related query-document pairs in a research prototype
\end{itemize}

\textbf{Design Trade-offs:}

The two-stage approach achieves optimal balance between speed and accuracy:
\begin{itemize}
    \item \textbf{Efficiency:} Avoids exhaustive cross-encoding of the entire corpus by reranking only a small candidate set
    \item \textbf{Precision:} Allows the system to refine FAISS candidates before selecting the examples sent to the LLM
    \item \textbf{Scalability:} Keeps reranking limited to a small candidate set rather than applying an expensive model to the full corpus
\end{itemize}

\textbf{Integration with Pipeline:}

Reranking is implemented as an optional enhancement controlled through configuration flags (\texttt{use\_reranker=True}). This modular design enables controlled experiments comparing:
\begin{itemize}
    \item Baseline: FAISS retrieval only (top-3 directly from embedding similarity)
    \item Enhanced: FAISS + Cross-encoder reranking (refined examples selected from a retrieved candidate set)
\end{itemize}

The purpose of this design is to improve the semantic relevance of retrieved examples before they are provided to the LLM, thereby increasing the chance that the generated letter follows an appropriate structure and register.

\subsection{Transformer Model}

The methodology includes transformer-based Named Entity Recognition (NER) for two critical functions: (1) extracting structured information from user prompts, and (2) anonymizing the letter corpus before embedding to remove personal identifiers that could bias retrieval.

\textbf{Model Selection - XLM-RoBERTa:}

XLM-RoBERTa-base was selected as the foundation model for NER tasks due to its strong cross-lingual transfer capabilities. Unlike English-centric BERT, XLM-RoBERTa was pretrained on 2.5TB of CommonCrawl data across 100 languages, including Sinhala \cite{conneau2019unsupervised}. This multilingual pretraining provides contextual representations that capture Sinhala linguistic structure without requiring language-specific model development.

\textbf{Architecture Specifications:}
\begin{itemize}
    \item \textbf{Model:} xlm-roberta-base
    \item \textbf{Parameters:} 270 million
    \item \textbf{Layers:} 12 transformer encoder layers
    \item \textbf{Hidden Dimension:} 768
    \item \textbf{Tokenization:} SentencePiece BPE with 250K vocabulary
    \item \textbf{Max Sequence Length:} 512 tokens
\end{itemize}

\textbf{Fine-Tuning Approach:}

The base XLM-RoBERTa model is fine-tuned on Sinhala letter data for token-level classification using the BIO (Begin-Inside-Outside) tagging scheme. The model learns to identify entity types critical for letter generation:

\begin{itemize}
    \item \textbf{LETTER\_TYPE:} Category classification across formal letter types such as request, application, complaint, invitation, appreciation, recommendation, inquiry, transfer, and leave
    \item \textbf{RECIPIENT:} Intended recipient of the letter
    \item \textbf{SENDER:} Letter sender identification
    \item \textbf{SUBJECT:} Subject line or main topic
    \item \textbf{PURPOSE:} Primary intent or reason for writing
    \item \textbf{DETAILS:} Supporting details required to make the generated letter specific and useful
    \item \textbf{DATE/TIME/VENUE:} Event-related information for invitation and event-based letters
\end{itemize}

\textbf{Training Configuration:}
\begin{itemize}
    \item Training corpus: 150 annotated Sinhala letters
    \item Train/validation split: 80/20 (120 training, 30 validation)
    \item Epochs: 5
    \item Batch size: 16
    \item Learning rate: 2e-5 with linear warmup
    \item Optimizer: AdamW with weight decay
\end{itemize}

\textbf{Dual-Purpose Design:}

\textbf{1. Information Extraction NER:}
Extracts structured fields from informal user prompts to populate letter templates. For example, from the prompt "මම අසනීපෙන් නිසා නිවාඩුවක් අවශ්‍යයි", the model identifies \texttt{letter\_type=request} and \texttt{purpose}="අසනීප නිවාඩුවක්".

\textbf{2. LLM-Based Backup Extraction:}
Because user prompts may be short, informal, ambiguous, or written in mixed Sinhala-English forms, a schema-guided LLM extractor is used as a backup strategy. If the transformer-based extractor fails to populate required fields, the LLM is prompted to return a structured JSON object containing the same schema fields. This hybrid strategy combines the speed and determinism of NER with the contextual reasoning ability of LLMs.

\textbf{3. Privacy-Preserving NER:}
Detects and replaces personal entities (names, locations, organizations) in the corpus before embedding. This ensures FAISS retrieval focuses on structural and semantic patterns rather than entity-specific content. Original text "මම සුනිල් පෙරේරා මොරටුව විශ්වවිද්‍යාලයට..." becomes "මම <PERSON> <ORGANIZATION>ට..." before vectorization.

\textbf{Design Rationale:}

Transformer-based NER was chosen over rule-based extraction (regex patterns) because:
\begin{itemize}
    \item \textbf{Robustness:} Handles linguistic variations and informal language
    \item \textbf{Context Awareness:} Disambiguates entities based on surrounding context
    \item \textbf{Generalization:} Performs well on unseen phrases not covered by fixed patterns
\end{itemize}

The NER component is therefore used as a structured extraction and anonymization mechanism, while the LLM backup strategy improves robustness when the prompt contains implicit information that is difficult to capture using token-level entity extraction alone.

\subsection{Text Generation: Plug-and-Play LLM Architecture}

A key design principle of this research is that the text generation component is built as a \textbf{provider-agnostic, plug-and-play LLM architecture}. Rather than coupling the pipeline to any specific model, the system defines a unified interface through which any supported LLM provider can be swapped in via configuration alone—without any code changes. This design serves two purposes: it allows the research to evaluate and compare different multilingual LLMs on the Sinhala letter generation task, and it ensures the system remains adaptable as the field of multilingual NLP continues to evolve.

\subsubsection{Multi-Provider LLM Factory}

The system implements an \texttt{LLMFactory} pattern that centralises LLM initialisation across all five pipeline steps. Supported providers are enumerated as follows:

\begin{itemize}
    \item \textbf{Google Gemini} — accessed via the Google Generative AI API (e.g., \texttt{gemini-2.5-flash})
    \item \textbf{Ollama} — local open-source inference framework supporting models such as Aya 8B (\texttt{aya:8b}), LLaMA, Mistral, and others
    \item \textbf{OpenAI} — standard OpenAI REST API (e.g., GPT-4o)
    \item \textbf{Azure OpenAI} — enterprise-grade OpenAI deployment via Azure
    \item \textbf{HuggingFace} — models loaded directly from the HuggingFace Hub
\end{itemize}

The active provider is selected through a single configuration parameter. The factory reads the provider enum, loads the corresponding credentials from environment variables, and returns a LangChain-compatible LLM object that integrates transparently with the rest of the pipeline. This means that switching from one model or provider to another requires only a one-line configuration change—no modifications to extraction, retrieval, or generation logic are needed.

\subsubsection{Separation of Extraction and Generation Models}

The architecture supports using \textit{different} providers for the two LLM-dependent steps in the pipeline: information extraction (Step 1) and letter generation (Step 5). This separation is intentional: the requirements for each step differ significantly. Information extraction benefits from fast, instruction-following models with structured output capabilities, while letter generation requires strong multilingual fluency and coherent long-form output. The configuration system allows each step to be independently assigned a provider and model.

\subsubsection{Current Default Configuration}

The pipeline is currently configured to use \textbf{Google Gemini 2.5 Flash} as the default model for both extraction and generation, accessed via the LangChain Google Generative AI integration. Gemini 2.5 Flash offers strong multilingual capability, including Sinhala, with low latency and no local GPU requirements.

For researchers wishing to run the system in a fully local, offline environment, the Ollama provider with the \textbf{Aya 8B} model (\texttt{aya:8b}) is supported as an alternative. Aya 8B (Aya-23) is an open-source multilingual model covering 23 languages; the related Aya-101 model extends coverage to 101 languages including Sinhala. Either Aya variant can be deployed locally using the Ollama inference framework, which provides a REST API, efficient model loading, and memory management without any external API dependencies. For local Sinhala generation, the retrieval-augmented context supplied by the pipeline helps compensate for the limited Sinhala exposure of the smaller 8B variant.

\subsubsection{Design Rationale}

The plug-and-play design reflects a deliberate research stance: rather than evaluating the performance of one specific LLM on Sinhala letter generation, this work evaluates the \textit{RAG pipeline approach} itself—measuring how much retrieval-augmented context improves generation quality, regardless of the underlying model. By keeping the model layer interchangeable, the system allows the same experimental setup to be replicated with different LLMs, enabling future comparative studies across multilingual model families.

This architecture also aligns with reproducibility goals: researchers with access to different infrastructure (GPU-enabled local machines, cloud APIs, or enterprise deployments) can run the same pipeline using the provider most suited to their environment.

\subsection{Metadata Filtering}

Metadata filtering serves as a complementary retrieval mechanism alongside vector similarity search. While FAISS retrieves documents based on semantic embedding similarity, metadata filtering enables precise categorical constraints to improve retrieval precision and interpretability.

\textbf{Metadata Schema Design:}

The letter corpus is augmented with structured metadata fields derived from the CSV schema:

\begin{itemize}
    \item \textbf{letter\_category:} Taxonomic classification (request, application, complaint, invitation, appreciation, general, notification)
    \item \textbf{doc\_type:} Document structure type
    \begin{itemize}
        \item \textit{example:} Complete letter ready for reference
        \item \textit{structure:} Template with placeholders
        \item \textit{section\_template:} Reusable components (greetings, closings)
    \end{itemize}
    \item \textbf{register:} Formality level (formal, very\_formal)
    \item \textbf{source:} Data provenance (synthetic, curated, user\_generated)
    \item \textbf{tags:} Free-form descriptive keywords
    \item \textbf{rating:} Quality score (1-5) for user-generated content
\end{itemize}

\textbf{Implementation Approach:}

The system employs an in-memory metadata filtering approach using synchronized data structures:

\begin{itemize}
    \item \textbf{FAISS Index:} Stores 768-dimensional embedding vectors
    \item \textbf{Metadata DataFrame:} Stores structured metadata aligned by index position
    \item \textbf{Corpus Texts:} Stores original letter content
\end{itemize}

These three structures maintain a strict synchronization invariant: document at FAISS index position \textit{i} corresponds to metadata row \textit{i} and corpus text \textit{i}.

\textbf{Hybrid Retrieval Strategy:}

The system combines vector search with metadata constraints through the following process:

\begin{enumerate}
    \item \textbf{Vector Search:} FAISS retrieves a candidate set using semantic similarity between the Sinhala-aware query and indexed document chunks.
    \item \textbf{Metadata Filtering:} The candidate set is filtered using metadata constraints such as \texttt{letter\_category} and \texttt{doc\_type}.
    \item \textbf{Bucketed Retrieval:} The system separately retrieves one structure template and a small number of complete example letters so that the final prompt receives both format guidance and content guidance.
    \item \textbf{Fallback Retrieval:} If no category-specific document is found, the system falls back to unfiltered documents of the same document type, preventing generation from failing due to sparse category coverage.
\end{enumerate}

\textbf{Automatic Metadata Extraction:}

To enable automatic filtering, the system infers metadata constraints from user prompts:

\begin{itemize}
    \item Extracted \texttt{letter\_type} maps to \texttt{letter\_category} filter
    \item Keywords like "ආකෘතිය" (template) trigger \texttt{doc\_type=structure} filter
    \item Keywords like "විධිමත්" (formal) trigger \texttt{register=very\_formal} filter
\end{itemize}

\textbf{Quality-Based Filtering:}

As the system incorporates user-generated letters (rated $\geq$4 stars), metadata enables quality control by prioritizing high-rated examples in retrieval. This creates a self-improving feedback loop where well-received letters influence future generations.

\textbf{Design Rationale:}

For this research scope (150-document corpus), in-memory filtering was selected over graph databases (e.g., Neo4j) because:

\begin{itemize}
    \item \textbf{Simplicity:} Filtering operations are primarily simple categorical lookups rather than complex graph traversals
    \item \textbf{Performance:} DataFrame filtering operations complete in microseconds for small corpora
    \item \textbf{Reproducibility:} CSV-based metadata eliminates external database dependencies
    \item \textbf{Maintainability:} Reduces infrastructure complexity for research prototyping
\end{itemize}

The metadata schema is designed to support future extension to graph databases if corpus scale grows to thousands of documents, where relationship modeling (hierarchical categories, document similarity edges) would provide additional value.

\section{Embedding and Indexing Process}
The embedding and indexing process converts the cleaned Sinhala letter corpus into a searchable vector knowledge base. Each CSV row is converted into a document by combining the title and content fields, while the remaining fields are stored as metadata. This allows the retrieval system to search by semantic similarity while still preserving important document attributes such as category, document type, register, source, tags, and rating.

The document text is split into manageable chunks before embedding. Chunking prevents long letters from dominating the retrieval context and ensures that each retrieved unit remains focused enough to be useful in prompt construction. The chunks are then embedded using LaBSE and stored in a FAISS vector index. The index is saved locally so that the system can load it during runtime instead of rebuilding it for each request.

During inference, the extracted user intent is converted into a Sinhala-aware query and embedded using the same LaBSE model. FAISS retrieves semantically similar chunks, after which metadata filtering separates structure templates from example letters. This method ensures that the generated prompt contains both a formal letter structure and concrete examples of Sinhala formal writing.

\section{Generation Pipeline}
The generation pipeline begins after the system has extracted the user's intent and retrieved relevant documents from the knowledge base. The enhanced prompt given to the LLM contains four main components: the original user prompt, the structured metadata extracted from the prompt, the retrieved structure template, and the retrieved example letters. The structure template guides the format of the generated letter, while the examples provide stylistic and linguistic grounding in formal Sinhala.

The prompt construction step explicitly instructs the LLM to generate only in Sinhala, maintain formal written register, avoid code-mixing, and produce a complete letter rather than a summary or explanation. This is important because general-purpose multilingual LLMs may otherwise mix English terms, omit formal letter sections, or produce informal Sinhala.

The pipeline is model-agnostic. The generation model is selected through configuration and may be a cloud-based model such as Google Gemini or OpenAI, an Azure OpenAI deployment, a HuggingFace model, or a locally hosted Ollama model such as Aya 8B. This design allows the same RAG pipeline to be evaluated across different LLM providers without changing the retrieval or prompt construction logic.

Following generation, the output can be evaluated by users or expert evaluators. High-quality generated letters can be anonymized and added back to the knowledge base as user-generated examples, allowing the corpus to grow over time. Automatic prompt optimization based on feedback is not part of the current methodology and is treated as a possible extension for future work.

\section{Methodological Limitations}

Several methodological limitations must be acknowledged. First, although the retrieval corpus contains curated Sinhala formal letters across the selected letter categories, it is still small compared with large-scale corpora available for high-resource languages. This limits the diversity of examples that can be retrieved for rare or highly specific user requests. Secondly, the corpus is manually curated and therefore depends on the quality and representativeness of the selected letters.

Thirdly, OCR and manual preprocessing may introduce minor transcription or normalization errors, especially when working with scanned Sinhala documents. These errors can affect both embeddings and generated output if not identified during manual review. Fourthly, the generated quality depends partly on the selected LLM provider. The RAG design reduces this dependency by grounding the model in retrieved examples, but it does not completely remove differences between LLMs.

Finally, Sinhala formal writing quality involves subjective judgement. Grammar, register, politeness, and cultural appropriateness may be interpreted slightly differently by different evaluators. The number of expert evaluators is also limited by availability. For this reason, the evaluation design uses multiple expert evaluators and inter-rater reliability analysis, as described in the Evaluation chapter.

\subsection{Request Flow}

The normal user request flow consists of three backend calls. First, the frontend submits the user's prompt to \texttt{/process\_query/}. \subsection{Information Extraction Methods}

Information extraction is a critical component of the letter generation pipeline, responsible for parsing user prompts (often informal Sinhala text) into structured fields such as letter type, recipient, subject, and purpose. This research implements and evaluates two distinct extraction approaches: (1) a fine-tuned Named Entity Recognition (NER) model using transformer architectures, and (2) LLM-based extraction using schema-first prompting through the plug-and-play LLM factory described in the Methodology chapter.

\subsubsection{NER-Based Extraction}

\textbf{Model Architecture and Training}

A Named Entity Recognition model was fine-tuned using XLM-RoBERTa-base (multilingual transformer) to identify and extract structured information from Sinhala letter requests. XLM-RoBERTa was selected for its strong cross-lingual transfer capabilities and proven performance on low-resource languages.

\textbf{Training Dataset Preparation:}

The training dataset was curated from 150 official Sinhala letters using a semi-automated pattern-based approach:

\begin{enumerate}
    \item \textbf{Pattern Extraction:} Common phrases and structural patterns were identified from the letter corpus (Figure \ref{fig:impl_ner_patterns})
    \item \textbf{Entity Annotation:} Manual labeling of entity spans for each letter component
    \item \textbf{Data Structuring:} Conversion to token-level BIO (Begin-Inside-Outside) format
\end{enumerate}

\begin{figure}
    \centering
    \includegraphics[width=1\linewidth]{images/letter_patterns.png}
    \caption{Letter structuring patterns used for NER training data preparation}
    \label{fig:impl_ner_patterns}
\end{figure}

\textbf{Entity Schema:}

The NER model was trained to recognize nine entity types critical for letter generation:

\begin{SinhalaVerbatim}
Entity Types:
- LETTER_TYPE: Letter category
- RECIPIENT: Intended recipient (e.g., කළමනාකරු, අධ්‍යක්ෂ)
- SENDER: Letter sender name
- SUBJECT: Subject line or main topic
- PURPOSE: Primary intent or reason for writing
- DETAILS: Supporting information
- EVENT_DATE: Event date for invitation or event-based letters
- EVENT_TIME: Event time for invitation or event-based letters
- EVENT_VENUE: Event venue for invitation or event-based letters
\end{SinhalaVerbatim}

\textbf{Training Configuration:}

\begin{itemize}
    \item Base model: xlm-roberta-base (270M parameters)
    \item Training samples: 150 annotated Sinhala letters
    \item Training epochs: 5
    \item Batch size: 16
    \item Learning rate: 2e-5 with linear warmup
    \item Optimizer: AdamW
    \item Loss function: Cross-entropy over token classifications
    \item Validation split: 80/20 train-validation split
\end{itemize}

\textbf{Post-Processing Pipeline:}

Raw NER outputs undergo structured conversion:
\begin{enumerate}
    \item Extract token-level predictions (BIO tags)
    \item Group consecutive tokens with same entity type
    \item Resolve entity boundaries and extract spans
    \item Convert to JSON schema matching downstream requirements
    \item Validate required fields and apply defaults for missing values
\end{enumerate}

\subsubsection{LLM-Based Extraction}

\textbf{Schema-First Prompting Architecture}

The LLM-based extraction leverages the instruction-following capabilities of the configured LLM through schema-first prompting. This approach does not require training data or model fine-tuning—instead, it provides the model with an explicit JSON schema definition that guides the extraction process. Because extraction is handled through the LLM factory, any supported provider can serve as the extraction model without changes to the extraction logic.

\textbf{Output Validation and Cleaning:}

LLM outputs undergo several validation steps:

\textbf{Key Advantages of Schema-First Approach:}

\begin{itemize}
    \item \textbf{Simplicity:} No need to maintain multiple example pairs
    \item \textbf{Consistency:} Schema serves as the single source of truth
    \item \textbf{Maintainability:} Field changes require only schema updates
    \item \textbf{Token Efficiency:} Shorter prompts (schema only vs. schema + examples)
    \item \textbf{Multilingual Clarity:} Sinhala field descriptions guide extraction directly
\end{itemize}

\textbf{Code Implementation:}

The extraction step is implemented using a LangChain chain, making it provider-agnostic. The extraction LLM is injected at pipeline initialisation time and can be any supported provider (Gemini, Ollama, OpenAI, etc.):

\begin{SinhalaVerbatim}
def _extract_with_llm(self, text: str) -> dict:
    """Extract information using the configured LLM via LangChain"""
    extraction_prompt = f"""
    මෙම සිංහල ලිපි ඉල්ලීමෙන් ප්‍රධාන තොරතුරු උපුටා ගන්න.

    පහත JSON ආකෘතිය භාවිතා කරන්න:
    {self.extraction_schema}

    දැන් මෙම ඉල්ලීම විශ්ලේෂණය කරන්න:
    {text}

    වලංගු JSON පමණක් ප්‍රතිදානය කරන්න:
    """
    prompt_template = ChatPromptTemplate.from_template("{prompt}")
    chain = prompt_template | self.llm | StrOutputParser()
    response = chain.invoke({"prompt": extraction_prompt})
    extracted = json.loads(self._clean_json_text(response))
    return self._coerce_to_schema(extracted)
\end{SinhalaVerbatim}

The \texttt{self.llm} object is initialised by the \texttt{LLMFactory} at startup and is fully interchangeable. Rate-limit errors (HTTP 429) from API-based providers are handled automatically with exponential backoff (up to 4 retries, base delay 5 seconds).

\subsubsection{Hybrid Extraction Strategy}

The implemented extraction layer supports both NER-based and LLM-based extraction. The NER model provides fast structured extraction where entity spans can be identified directly. The LLM-based extractor provides a backup strategy for informal prompts, implicit requests, mixed-script input, or prompts where required fields are not explicitly stated. This hybrid design allows the system to combine deterministic extraction with contextual reasoning.

\subsection{Named Entity Recognition for Data Privacy}

The Named Entity Recognition (NER) module for data privacy serves a distinct purpose from the extraction NER discussed earlier in this chapter. While extraction NER identifies entities in user prompts, the privacy NER preprocesses the letter corpus by removing personal identifiers before embedding into the FAISS vector store.

\subsubsection{Purpose and Motivation}

Personal or location-specific entities (names, institutions, addresses) in the letter corpus can introduce unintentional bias into the retrieval process. For example, if a letter contains "මොරටුව විශ්වවිද්‍යාලය" (University of Moratuwa), the system might incorrectly associate all university-related requests with Moratuwa specifically. By removing these entities, the embeddings capture only structural and contextual patterns—enabling generalization across different contexts.

\subsubsection{Implementation Approach}

\textbf{Model Architecture:}
\begin{itemize}
    \item Base model: xlm-roberta-base (270M parameters)
    \item Entity types detected: PERSON, LOCATION, ORGANIZATION, DATE
    \item Training approach: Fine-tuned on Sinhala entity-annotated corpus
    \item Integration: spaCy pipeline with custom rule-based enhancements
\end{itemize}

\textbf{Training Configuration:}

\begin{itemize}
    \item Training samples: 120 annotated Sinhala letters
    \item Training epochs: 3
    \item Batch size: 8
    \item Learning rate: 2e-5
    \item Loss function: Token-level cross-entropy
\end{itemize}

\textbf{Entity Replacement Strategy:}

Detected entities are replaced with generic placeholders to preserve sentence structure:
\begin{itemize}
    \item PERSON → \texttt{<person>}
    \item LOCATION → \texttt{<location>}
    \item ORGANIZATION → \texttt{<organization>}
    \item DATE → \texttt{<date>}
\end{itemize}

\textbf{Example Preprocessing:}

\textbf{Original:}
\begin{SinhalaVerbatim}
"මම සුනිල් පෙරේරා. මොරටුව විශ්වවිද්‍යාලයට 2024 ජනවාරි මස 15 වැනිදා
සහභාගි වීමට කැමතියි."
\end{SinhalaVerbatim}

\textbf{After NER Privacy Processing:}
\begin{SinhalaVerbatim}
"මම <person>. <organization>ට <date> සහභාගි වීමට කැමතියි."
\end{SinhalaVerbatim}

This anonymized text is then embedded into FAISS, ensuring retrieval focuses on intent (enrollment request) rather than specific entities.

\subsubsection{Preprocessing Pipeline Integration}

The NER privacy module operates during corpus preparation (before embedding):
\begin{enumerate}
    \item Load raw letter corpus (150 Sinhala letters)
    \item Run NER model on each letter body
    \item Replace detected entities with placeholders
    \item Generate embeddings using multilingual sentence transformer
    \item Store anonymized embeddings in FAISS index
\end{enumerate}

\textbf{Code Implementation:}

\begin{verbatim}
def anonymize_entities(text: str, ner_model) -> str:
    """Remove named entities for privacy preservation"""
    entities = ner_model(text)
    anonymized = text
    for entity in sorted(entities, key=lambda e: e.start, reverse=True):
        placeholder = f"<{entity.label.lower()}>"
        anonymized = (anonymized[:entity.start] + 
                     placeholder + 
                     anonymized[entity.end:])
    return anonymized
\end{verbatim}

\subsubsection{Impact on Retrieval Quality}

Testing showed that entity anonymization improved generalization:
\begin{itemize}
    \item \textbf{Before Anonymization:} Query "විශ්වවිද්‍යාලයට ඇතුළත් වීමට අවශ්‍යයි" retrieved only Moratuwa University examples
    \item \textbf{After Anonymization:} Same query retrieved diverse university enrollment letter patterns
    \item \textbf{Precision Improvement:} 12\% increase in retrieval relevance for generic queries
\end{itemize}

This demonstrates the value of entity removal for creating generalizable letter templates that adapt to user-specific contexts during generation.

\section{RAG Pipeline}

The RAG pipeline is implemented as a modular orchestration managed by a central \texttt{Pipeline} class. The pipeline exposes a two-part interface to the FastAPI layer: \texttt{process()}, which runs Steps 1–4 and returns either an enhanced prompt or a set of clarifying questions, and \texttt{generate\_letter()}, which runs the generation step. A sixth post-generation step is handled through the feedback flow, where high-rated generated letters are anonymized and added back to the knowledge base.

\subsection{Step 1: Information Extraction}

The first step parses the user's informal Sinhala prompt into a structured metadata object. As described earlier, this is implemented using transformer-based NER with LLM-based schema-first extraction as a backup strategy. The extracted fields—letter type, recipient, sender, subject, purpose, details, and optional event fields (date, time, venue)—are passed to the next step for validation.

\subsection{Step 2: Gap Detection}

The gap detection step validates the extracted metadata against a predefined set of required fields for each letter type. For example, an \textit{invitation} letter requires event date, time, and venue fields in addition to the standard recipient, sender, and purpose fields. If any required fields are missing, the system generates type-specific clarifying questions in Sinhala (e.g., "උත්සවය පැවැත්වෙන ස්ථානය කුමක්ද?" for a missing venue field) and returns them to the user. The pipeline halts at this step until all required information is collected through the multi-turn dialogue.

\subsection{Step 3: Document Retrieval}

Once all required fields are present, the retrieval step constructs a semantic search query from the extracted metadata using the \texttt{SinhalaQueryBuilder}. This component maps English field values to their Sinhala equivalents and enriches the query with formal language indicators and letter-type-specific terminology, improving the semantic alignment between the query and the Sinhala letter corpus.

The retrieval strategy follows a two-part approach:
\begin{enumerate}
    \item One structure template matching the letter category is retrieved from the knowledge base. Structure templates define the skeletal sections of formal Sinhala letters and guide the overall layout of the generated output.
    \item Two example letters matching the letter category are retrieved. If the reranker is enabled, the initial top-20 candidates from FAISS are re-scored by the cross-encoder model (\texttt{cross-encoder/ms-marco-MiniLM-L-6-v2}) and the final top-2 are selected based on relevance. If no category-specific documents are found, the retrieval falls back to unfiltered results.
\end{enumerate}

\subsection{Step 4: Prompt Construction}

The prompt builder combines all available context into a structured enhanced prompt. The prompt includes:
\begin{itemize}
    \item A system instruction in Sinhala identifying the assistant's role as a formal letter writing assistant
    \item The structured letter details extracted in Step 1 (type, recipient, sender, subject, purpose, details, and any event-specific fields for invitations)
    \item The retrieved structure template and example letters, separated by delimiters, with instructions to use them as reference for structure and formal language
    \item Explicit generation instructions covering letter completeness, grammar, punctuation, formal register (ලිඛිත භාෂාව), and prohibition of code-mixing
\end{itemize}

This enhanced prompt is returned to the API layer, which then calls the \texttt{generate\_letter()} endpoint to proceed to Step 5.

\section{Letter Generation Pipeline}

The letter generation pipeline contains Step 5 and Step 6 of the implemented workflow.

\subsection{Step 5: LLM-Based Letter Generation}

Step 5 implements letter generation as a LangChain chain:

\begin{verbatim}
prompt_template = ChatPromptTemplate.from_template("{enhanced_prompt}")
chain = prompt_template | self.llm | StrOutputParser()
letter = chain.invoke({"enhanced_prompt": enhanced_prompt})
\end{verbatim}

The \texttt{self.llm} object is the generation LLM initialised by the \texttt{LLMFactory} at startup. The chain passes the enhanced prompt directly to the model and returns the raw string output. Because all context structuring and instruction embedding is handled in Step 4, Step 5 requires only a clean LLM invocation. The model-agnostic design means the same generation step works identically with any supported provider.

The generation step can also receive sender profile information from the frontend. When sender information is available, the generator appends it to the enhanced prompt so that the final letter can include the user's name, title, address, phone number, and other sender details.

\subsection{Step 6: Feedback and Knowledge-Base Update}

Following generation, the system returns the letter to the user interface, where the user can rate the output on a 1–5 scale across multiple quality dimensions. Letters rated 4 or above are passed through the NER privacy module to remove personal entities, then embedded using LaBSE and added to the live FAISS index. This feedback loop continuously expands the knowledge base with high-quality, user-validated examples, improving the quality of future retrievals over time.

\section{Configuration}

The implementation uses a centralised configuration module to control retrieval, embedding, LLM, vector-store, and NER behaviour. The active data file, FAISS index path, embedding model, reranker flag, and LLM providers are all defined through configuration. This allows experiments to switch between baseline, Sinhala-query-enhanced, and full-pipeline configurations without rewriting the pipeline code.

The default generation and extraction providers can be configured separately. For example, Gemini can be used for extraction while a locally hosted Aya 8B model can be used for generation. The same factory interface is used regardless of provider, making the pipeline reusable across cloud and local deployment environments.

\section{Feedback and Administration}

The feedback system records structured per-letter ratings and broader system feedback. Per-letter feedback captures quality dimensions such as overall quality, grammar, structure, relevance, and fluency. System feedback captures usability-level information such as whether the generated output was useful and whether the clarification questions helped the user complete the prompt.

The administrative dashboard provides access to aggregate statistics, individual letter ratings, system feedback entries, and CSV export functions. This supports both evaluation and future system improvement, as the feedback records can be analysed to identify recurring problems in extraction, retrieval, prompt construction, or generation.

\chapter{Evaluation}

\section{Evaluation Strategy}

The evaluation is designed to determine whether the proposed Retrieval-Augmented Generation pipeline improves formal Sinhala letter generation when compared with a standard LLM-only baseline. The same underlying language model is used in both conditions so that the comparison measures the effect of retrieval, structured extraction, gap filling, and prompt augmentation rather than differences between model families. The primary experimental setup uses Google Gemini 2.5 Flash as the generation model, while the implementation allows the same protocol to be repeated with other providers such as Ollama-hosted Aya 8B, OpenAI, Azure OpenAI, or HuggingFace models.

The evaluation combines four forms of evidence. First, a human expert evaluation compares baseline and RAG-generated letters. Secondly, pairwise preference judgements identify which output experts would actually choose to send. Thirdly, component-level checks evaluate information extraction and retrieval behaviour. Finally, user feedback collected through the implemented interface is used to analyse practical usability.

\subsection{Justification for Human Evaluation}

Human evaluation is used as the primary assessment method because the quality of formal Sinhala letters cannot be fully captured through automated text similarity metrics. Metrics such as BLEU, ROUGE, or chrF can measure surface-level overlap with reference texts, but they do not reliably assess whether a generated Sinhala letter uses the correct honorifics, formal written register, cultural conventions, or administrative structure. Since this research focuses on practical letter usability, native Sinhala expert judgement is necessary to evaluate grammatical correctness, structural adherence, contextual relevance, fluency, and politeness.

\section{Evaluation Limitations}

Several limitations must be considered when interpreting the evaluation results. First, the expert evaluation uses a limited number of evaluators because formal Sinhala writing expertise is not widely available. Secondly, Sinhala formal writing quality involves subjective judgement, especially for politeness, register, and naturalness. Thirdly, the prompt set contains 30 prompts, which provides practical coverage for an MSc thesis but cannot represent every possible formal letter scenario. Fourthly, the results are partly dependent on the selected LLM provider. Although the design compares baseline and RAG outputs using the same model, a different model may produce different absolute scores. Finally, the retrieval corpus remains small compared with resources available for high-resource languages, so rare or highly specialized letter contexts may not retrieve ideal examples.

\section{Summary}

The evaluation results support the hypothesis that retrieval augmentation improves formal Sinhala letter generation compared with direct LLM prompting. The completed expert evaluation shows higher RAG scores across all six human rating dimensions and a strong pairwise preference for SinhalaLipi output. The remaining component-level and user-feedback results provide additional evidence about extraction, retrieval, and deployed-system usability.

\chapter{Conclusion and Future Work}

\section{Overview}
This research set out to improve Large Language Model support for Sinhala, a low-resource language, by focusing on the practical and culturally important task of formal letter writing. It proposed and evaluated SinhalaLipi, a Retrieval-Augmented Generation (RAG) system that transforms informal user prompts into structurally correct, formally registered Sinhala letters by combining structured information extraction, missing-information collection, semantic retrieval over a curated Sinhala letter corpus, cross-encoder reranking, prompt augmentation, and provider-agnostic LLM generation. This chapter summarises the main findings, revisits the research questions and hypotheses, acknowledges the limitations, and outlines directions for future work.

\section{Revisiting the Research Questions}
The main research question asked how a retrieval-augmented generation approach can be used to generate high-quality formal Sinhala letters from informal user prompts. The proposed pipeline and its evaluation demonstrate that grounding a general-purpose multilingual LLM in retrieved Sinhala letter structures and examples produces letters that are consistently rated higher in grammar, structure, formality, fluency, and overall usability than direct LLM prompting.

The sub-questions are addressed as follows. First, the limitations of current LLMs for formal Sinhala text—weak formal register, structural errors, and grammatical and spelling weaknesses—were identified through the baseline condition and the expert evaluation, where the direct LLM baseline scored notably lower on grammar (2.89) and formality (2.94). Second, the combination of LaBSE embeddings and a FAISS index was shown to retrieve relevant Sinhala letter structures and examples, achieving a category hit rate of 93.3\% and a Precision@3 of 0.74. Third, the comparison against the standard LLM baseline, measured through human expert evaluation, showed statistically significant RAG improvements across all six rubric dimensions. Fourth, a human-centred rubric covering grammar, structure, contextual relevance, formality, fluency, and overall usability, complemented by pairwise preference judgements, proved effective for assessing letter quality in the absence of reliable automated metrics for Sinhala. Fifth, the principal limitations of applying RAG to a low-resource language such as Sinhala—small corpus size, sparse coverage of rare letter categories, dependence on OCR and manual curation quality, and residual dependence on the underlying LLM—were identified and analysed.

\section{Hypothesis Evaluation}
The evaluation provides strong evidence to reject the null hypothesis (H0). Across all six evaluation dimensions, the RAG-based system scored significantly higher than the direct LLM baseline, with paired tests significant at $p < 0.05$ for every metric and large effect sizes for grammar, structure, formality, fluency, and overall usability. Evaluators also preferred the RAG output in 82.7\% of pairwise comparisons. These results support the alternative hypothesis (H1) that a retrieval-augmented generation approach significantly improves the fluency, grammatical correctness, and contextual relevance of formal Sinhala letters compared with generation by a standard language model alone.

\section{Limitations}
The findings should be interpreted in light of several limitations discussed in the methodology and evaluation chapters. The retrieval corpus is small relative to high-resource language resources, limiting example diversity for rare or highly specialised requests. The evaluation relied on a limited number of expert evaluators, reflecting the scarcity of formal Sinhala writing expertise, and on a set of 30 prompts that, while representative, cannot cover every formal letter scenario. Formal Sinhala writing quality also involves subjective judgement of register and politeness. Finally, although the same model is used in both conditions so that the comparison isolates the effect of retrieval, the absolute quality of generated letters remains partly dependent on the chosen LLM provider.

\section{Future Work}
Several directions follow naturally from this work. The retrieval corpus can be expanded—through additional curation, the self-improving feedback loop, and OCR of further archival letters—to improve coverage of rare letter categories and increase example diversity. The plug-and-play LLM architecture makes it possible to run the same evaluation protocol with locally hosted models such as Aya 8B and with other providers, enabling a comparative study of model families on the Sinhala letter generation task. Post-generation grammar checking and automatic error correction, explicitly out of scope here, could further raise output quality once Sinhala grammatical error correction resources mature. Automatic, feedback-driven prompt optimisation could be added to the pipeline. Finally, the approach could be extended to other formal Sinhala text types—such as notices, minutes, and official reports—and to other South Asian low-resource languages, testing the generality of retrieval-augmented generation for formal writing in under-resourced settings.

\section{Concluding Remarks}
This research demonstrates that retrieval-augmented generation is an effective and practical strategy for improving formal text generation in a low-resource language without large-scale model training. By grounding a multilingual LLM in a curated corpus of formal Sinhala letters, SinhalaLipi produces letters that experts find substantially more usable than those generated by direct prompting. Beyond the specific task of letter writing, the work offers a reusable framework and a curated resource that can support continued progress in Sinhala natural language processing and serve as a template for similar efforts in other under-resourced languages.
